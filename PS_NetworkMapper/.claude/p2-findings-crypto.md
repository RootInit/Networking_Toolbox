## P2CRYPTO-001

- **Track**: DATA
- **File:line**: `lib/Protect-MapperFile.ps1:99-102` (decrypt branch) and `:132-135` (encrypt branch)
- **Severity**: HIGH
- **Confidence**: High (empirically reproduced with strace against the actual `pwsh` 7.6.2 binary used by this repo's dev shell)
- **Claim**: `Move-Item -Path $TempTargetPath -Destination $TargetPath -Force` is **not** an atomic rename when `$TargetPath` already exists (the in-place-overwrite case the fix's own comment calls out as the primary motivation — "matters most here since -OutputFile can equal -InputFile"). PowerShell's `Move-Item -Force` implements overwrite-of-existing-destination as two separate filesystem operations — `unlink($TargetPath)` followed by `rename($TempTargetPath, $TargetPath)` — not a single atomic replace syscall. Between those two calls there is a real (if narrow) window where `$TargetPath` does not exist at all.
- **Trigger**: Run `Protect-MapperFile.ps1 -Decrypt` (or encrypt) with `-OutputFile` equal to a path that already exists (the documented in-place case), and have the process die (kill -9, power loss, disk full triggering the rename to fail, a Windows AV/indexer holding a transient lock on the just-vacated path) in the interval between the `unlink` and the `rename`.
- **Evidence**: Reproduced directly:
  ```
  $ echo OLD > target.json.tmp ; echo OLD2 > target.json   # dest pre-exists, as in the in-place case
  $ strace -f -e trace=rename,unlink -o strace.log pwsh -NoProfile -Command \
      'Move-Item -Path "./target.json.tmp" -Destination "./target.json" -Force'
  $ grep -E 'rename|unlink' strace.log
  1534306 unlink("/tmp/movetest/target.json") = 0
  1534306 rename("/tmp/movetest/target.json.tmp", "/tmp/movetest/target.json") = 0
  ```
  Two syscalls, in that order, confirmed twice independently. This is `System.Management.Automation`'s `FileSystemProvider` implementation of `-Force`-based overwrite (delete-then-move), which is the same managed code path on Windows — there is no OS-level reason to expect the Windows build to collapse this into a single atomic `MoveFileEx(..., MOVEFILE_REPLACE_EXISTING)` call instead, since the delete-then-move sequence is implemented in the cross-platform cmdlet layer, not delegated to a single native replace API.
- **Invariant hit**: INV-DATA ("a saved topology file is never silently corrupted or unrecoverable... a failed decrypt/save never destroys the prior good file") and INV-NO-LOCKOUT.
- **Impact**: Directly contradicts both the fix's stated goal ("a partway failure... leaves no half-written $TargetPath behind instead of a truncated one") and Pass 1's fix-review judgment that the residual `.tmp`-cleanup gap was "cosmetic disk-clutter... does not violate INV-DATA (original file is untouched either way)". That judgment is now falsified by direct evidence: the original file is *not* untouched in every failure mode — it can be flat-out deleted, with only the (uncleaned, see P2CRYPTO-002) `.tmp` file surviving as the sole copy of the data. For the in-place decrypt/encrypt case this is the operator's only copy of that data, so a kill or lock-contention exactly in this window turns "target missing, but data recoverable by finding and renaming `$TargetPath.tmp`" into an unplanned manual-recovery incident, not the "old good version stays in place" guarantee the fix intended.
- **Repro**: See Evidence block above; run under `strace -f -e trace=unlink,rename` against `pwsh -Command 'Move-Item -Path a.tmp -Destination a -Force'` where `a` pre-exists. Observe `unlink(a)` completes before `rename(a.tmp, a)` starts — kill the process between the two (e.g. `strace -f ... -e signal=none` with a synchronized `kill` after the unlink line appears) to see `a` absent and `a.tmp` present.
- **Fix sketch**: Either (a) do the atomicity check in reverse: `Move-Item` the *old* target aside to a second temp name first (or simply don't pre-check "-Force" and instead let `Rename-Item`/`[System.IO.File]::Replace` be used, which on .NET does a true atomic replace-with-backup on Windows), or (b) accept the current approach but add a `finally`-block cleanup (see P2CRYPTO-002) plus documentation that a missing `$TargetPath` after a crash means "check for `$TargetPath.tmp`, it holds the real data" — cheaper than reimplementing atomic replace, but only mitigates confusion, doesn't restore true atomicity. Full fix: use `[System.IO.File]::Replace($TempTargetPath, $TargetPath, $null)` on Windows/`.NET`, which performs a true atomic replace (single `ReplaceFile` Win32 call) instead of `Move-Item -Force`'s delete-then-move.

## P2CRYPTO-002

- **Track**: DATA
- **File:line**: `lib/Protect-MapperFile.ps1:99-100`, `:132-133`
- **Severity**: MEDIUM
- **Confidence**: High (direct code comparison + reasoning; concurrency scenario not literally executed but the fixed-path collision is deterministic from the code, not speculative)
- **Claim**: The commit message for `efbc0df` claims this is "the same pattern as FleetCrawl.ps1's topology writes," but the port is incomplete on two counts that FleetCrawl.ps1 actually has:
  1. **No cleanup**: `FleetCrawl.ps1` wraps its temp-file+rename writes in a scope with a `finally` block (`lib/FleetCrawl.ps1:507-513`) that does `if (Test-Path $TempOutputFile) { Remove-Item -Path $TempOutputFile -Force }`. `Protect-MapperFile.ps1`'s new temp+rename lines have no `try`/`finally` at all — if `Move-Item` throws (including the P2CRYPTO-001 delete-then-move failure mode), the `.tmp` file is left behind with no cleanup path, ever (the script just exits after an uncaught exception).
  2. **Fixed, not unique, temp name**: `FleetCrawl.ps1`'s temp filename embeds `$ScanTimestamp` (`NetworkMap_$ScanTimestamp.tmp$OutputExtension`), unique per crawl run. `Protect-MapperFile.ps1`'s temp filename is simply `"$TargetPath.tmp"` — always the same path for a given target, with no run-unique component (PID, timestamp, GUID).
- **Trigger**: Two `Protect-MapperFile.ps1` invocations targeting the same `$TargetPath` running concurrently (e.g. an operator double-launches the script, or scripts a batch loop that races if launched with `&`/background jobs against the same file, or simply re-runs it in a second terminal while the first is still prompting for/processing a password on a large topology file).
- **Evidence**: Code comparison — `lib/FleetCrawl.ps1:119` (`$ScanTimestamp` in temp name) and `:507-513` (`finally { ... Remove-Item -Path $TempOutputFile -Force }`) vs. `lib/Protect-MapperFile.ps1:99,132` (`$TempTargetPath = "$TargetPath.tmp"`, no surrounding try/finally anywhere in the file).
- **Invariant hit**: INV-DATA (round-trip/no-silent-corruption) under concurrent access, and the disk-clutter concern Pass 1 flagged as cosmetic.
- **Impact**: Low likelihood (this is a standalone, password-prompting CLI tool per its own header comment — "Not part of the app's own runtime" — never invoked by `WebServer.ps1` or any other automation per repo-wide grep), but if it does happen, two processes writing `Out-File -Force` to the identical `$TargetPath.tmp` path can interleave, and whichever finishes its `Move-Item` last "wins," silently discarding the other invocation's output with no error to either operator. Combined with P2CRYPTO-001, a losing process's `Move-Item -Force` could also delete `$TargetPath` (unlink phase) moments before the winning process's `Move-Item` recreates it, momentarily and non-deterministically exposing a missing-file window during any run, not just a killed one. Independently verified as a real (if narrow) code-level collision, not present in the pattern's origin (`FleetCrawl.ps1`) it claims to mirror.
- **Repro**: Not exercised by running two real concurrent invocations (would require synchronizing two password prompts); established by direct code inspection: both branches unconditionally compute `$TempTargetPath = "$TargetPath.tmp"` with no uniqueness token, confirmed against `FleetCrawl.ps1`'s actual pattern which does include one.
- **Fix sketch**: Make the temp name unique (e.g. `"$TargetPath.$PID.tmp"` or a GUID suffix), and wrap the write+move in `try { ... } finally { if (Test-Path $TempTargetPath) { Remove-Item -Path $TempTargetPath -Force } }` to match the established `FleetCrawl.ps1` pattern the commit message claims to follow.

## Checked and ruled out (no finding)

- **Stray `.tmp` interfering with a later listing/load.** Traced whether a leftover `Protect-MapperFile.ps1` `.tmp` file (`NetworkMap_X.json.tmp` / `NetworkMap_X.json.enc.tmp`) could be picked up by `WebServer.ps1`'s snapshot picker. `lib/WebServer.ps1:656` filters `Where-Object { $_.Name -match '^NetworkMap_.*\.json(\.enc)?$' -and $_.Name -notmatch '\.tmp\.json(\.enc)?$' }`. Protect-MapperFile's temp suffix is appended *after* the real extension (`....json.tmp`), which doesn't even satisfy the first (inclusion) regex — it doesn't end in `.json`/`.json.enc` — so it's excluded from the snapshot list regardless of the `.tmp` exclusion clause. Not a bug (though incidentally: the exclusion clause itself is written for `FleetCrawl.ps1`'s naming convention, `....tmp.json`, and would silently fail to protect against a hypothetical future `.tmp` naming scheme that puts `.tmp` after the extension like `Protect-MapperFile.ps1` does — currently moot since Protect-MapperFile's temp files are excluded by the first clause anyway, not worth a separate finding).
- **Same-filesystem/same-directory atomicity precondition.** Re-verified: `$TempTargetPath = "$TargetPath.tmp"` is always in the same directory as `$TargetPath` (string concatenation on the full path, no directory change), so the temp file and target are guaranteed to be on the same volume. This part of the original CRYPTO-001 fix-review judgment holds.
- **CRYPTO-002 comment fix — round-trip integrity.** Diffed `efbc0df`'s change to `web-src/topology-crypto.js`: it is a pure comment edit (iteration-count doc value 200,000 → 600,000, matching `lib/TopologyCrypto.ps1:14`'s actual `Get-TopologyPbkdf2Iterations` return value of `600000`). No code line changed. `MIN_ITERATIONS`/`MAX_ITERATIONS`/all decrypt logic byte-for-byte identical to pre-fix. Confirmed no accidental logic change.
- **CFG-003 new tests — correctness.** Read all 9 new guard-clause tests in `web-src/test/topology-crypto.test.mjs` (version/kdf/cipher/macAlgorithm/iterations-range/non-integer). Each asserts against the actual validation branches present in `topology-crypto.js:43-51`, error messages match exactly (`Unsupported envelope version`, `Unsupported encryption parameters`, `Iteration count out of range`), and the MIN_ITERATIONS boundary test (999 rejected) matches the real `MIN_ITERATIONS = 1000` constant. Ran the full suite: `cd web-src && node --test` → 91/91 pass, 0 fail. No stale/incorrect assertions found.
- **`lib/TopologyCrypto.ps1` consistency (unchanged file).** Re-read in full; `Get-TopologyPbkdf2Iterations` (600000), envelope validation bounds (`1000`/`5000000`, matching JS `MIN_ITERATIONS`/`MAX_ITERATIONS` exactly), and the numeric-type/range checks (`$IsNumericType`, `[long]` cast-and-compare guard against non-integer/out-of-range `iterations`) are all still consistent with `topology-crypto.js`'s mirrored logic. No drift introduced by this pass's changes (this file wasn't touched by `efbc0df`).

Both findings above (P2CRYPTO-001, P2CRYPTO-002) directly re-open and supersede Pass 1's "cosmetic disk-clutter... does not violate INV-DATA" judgment on the residual `.tmp`-cleanup item: independent re-verification shows the failure mode is not cosmetic — the delete-then-move sequence Move-Item actually performs means the *target* file, not just the temp file, is at risk during the overwrite-existing-destination case, which is exactly the in-place-decrypt/encrypt case the fix was written to protect.
