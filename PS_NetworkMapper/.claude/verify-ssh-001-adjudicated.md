# Adjudication — SSH-001 / SSH-002

## Verdict: HIGH (both SSH-001 and SSH-002)

Confirmed real by all three reviews (unescaped `$Username` reaching `ProcessStartInfo.Arguments`/`cmd.exe /c` with zero validation — not disputed). This adjudication resolves severity only, and lands between the two verifiers, but for a specific evidentiary reason, not as a split-the-difference average.

## What I independently checked

1. **Localhost binding**: confirmed, `lib/WebServer.ps1:815-816` binds `http://localhost:$Port/` only (default port 8787, fixed and predictable, set in `Start-NetworkMapper.ps1:16`). Verifier A is correct that this is not remotely reachable over the network.

2. **CSRF/origin gating on `/api/save-config` specifically**: confirmed present and correctly wired, not just claimed. `lib/WebServer.ps1:987-993` gates the save-config route behind `Test-SameOriginRequest` (`WebServer.ps1:116-124`), which checks the `Origin` header (falling back to `Referer`) against `http://localhost:$Port` and fails closed if neither header is present. This does block the scenario in prompt item #2: a malicious webpage the operator's browser visits cannot make a same-origin-looking `fetch()`/form POST to `/api/save-config`, because a browser sets the `Origin` header itself and page JS cannot override it. So the classic "malicious website CSRFs the operator's browser" angle is **not** the live vector here — Verifier A's localhost-binding argument extends further than just "no remote attacker": the browser-CSRF door is also shut, by design, with the reasoning documented in-repo.

3. **The gap the code's own comment identifies, and that neither verifier weighed**: `WebServer.ps1:108-115` states outright — *"Does NOT cover a hostile process running as a different OS user on the same machine - it can set any Origin it likes talking directly to this HttpListener. Pre-existing, app-wide gap."* This is not a browser; it's any local process (a different Windows account, a compromised low-privileged scheduled task, another logged-in user on a shared/RDP host, or malware running as a different principal) that speaks raw HTTP. Such a caller can trivially set `Origin: http://localhost:8787` itself — there is no browser between it and the listener to prevent that — and there is **no other check at all**: no auth token, no API key, no password, grepped and confirmed absent from `WebServer.ps1`. That process can POST a malicious `credentials.username` to `/api/save-config` and then trigger `/api/connect` or `/api/scan-network`, landing directly in the SSH-001/SSH-002 sink.

## Why this changes the call from Medium

Verifier A's "self-injection, no privilege boundary crossed" framing is only true for the browser-CSRF angle, which is in fact mitigated. It is not true for the raw-HTTP-from-a-different-local-principal angle, which the codebase's own author flagged as an open gap and which this bug directly weaponizes: a local principal *without* code-execution rights as the WebServer's OS user — and thus without access to the plaintext switch password, the decrypted `Configuration.json.enc`, or the ability to just click "Launch SSH Session" themselves — can nonetheless reach RCE *as* that user via this exact injection, because nothing else stands between "reaches localhost:8787" and "controls the argv/shell string that spawns ssh.exe/cmd.exe." That is a genuine privilege boundary crossing: gaining code execution and thereby the plaintext credentials and full fleet reachability that the target user already holds, starting from a principal who did not have that access. Verifier B is correct that this clears the bar for a serious, cross-principal-reachable RCE and should not be downgraded to a same-principal robustness bug; Verifier A is correct that it is not "any unauthenticated network attacker, full stop" as the original finding's Trigger/Impact text implies, since the listener genuinely is localhost-only and the browser-CSRF path genuinely is gated.

## Why not CRITICAL

Reaching the vulnerable code path still requires *some* local presence on the host running `WebServer.ps1` — either as a distinct OS principal issuing raw HTTP (not a passive drive-by), or the fully-consenting-operator self-attack case, which by itself adds little beyond what that principal already has. It is not exploitable by a pure remote/unauthenticated network attacker with no foothold on the box at all, which is what CRITICAL should be reserved for in this codebase's threat model (compare: a remotely-reachable RCE with no local presence required). The worst realistic outcome — a different local OS principal escalating to the credential-holder's identity and thereby to plaintext SSH access across the entire switch fleet, silently and repeatedly (SSH-002 fires on every fleet-crawl worker) — is severe enough to keep this above Medium, but the requirement of local host presence by a non-operator principal keeps it below Critical.

## Disposition

- **SSH-001**: HIGH (confidence High). Real cross-principal RCE vector via same-machine-but-different-OS-user raw HTTP request against an unauthenticated, token-less endpoint; not the "any network attacker" framing of the original report, but more than a same-principal robustness gap.
- **SSH-002**: HIGH (confidence High), same reasoning, with the additional note (per both verifiers) that it is the more robust/lower-skill payload (cmd.exe metacharacters vs. ssh getopt ordering) and fires automatically on every fleet-crawl worker rather than requiring an interactive click — the recurring, unattended trigger surface is itself an aggravating factor within HIGH.
- **Fix priority**: both the input-validation fix (reject non-Junos-legal characters in `Username` at `Invoke-SaveConfigAction`) and the `ArgumentList`/native-redirection process-invocation fix from the original report's "Fix sketch" remain the correct remediation, unchanged by this severity adjudication. Independently worth flagging to the maintainers: the documented `Test-SameOriginRequest` gap (raw HTTP from a different local OS user bypasses the Origin check entirely) is the actual mechanism that elevates this beyond self-attack, and deserves its own tracking (e.g., a shared-secret/localhost-only auth token issued at process start and required on every state-changing endpoint) rather than being left as an accepted "pre-existing, app-wide gap."
